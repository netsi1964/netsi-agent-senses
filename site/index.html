    Alpha · Claude Code plugin · Apache-2.0

    Give your AI agent senses.

    Pain when tool calls keep failing. A feel for how full its context is. A sense of time. A nose for code smells. And a gut feeling that sums it all up. Readable by the agent, tunable by you.

    pain interoception time smell gut
    Install in 5 minutes → Why senses?
    Motivation

    Agents don't feel how a session is going.

    A human developer notices when things go wrong: the third failing build stings, a long afternoon feels long, a messy diff smells. An AI agent has none of that. It notices a failure spiral, a nearly full context or a two-hour solo run only when it is too late.

    For the agent

    A compact, structured picture of its own state that it can read over MCP and act on: change approach, summarise, check in with you.

    For you

    A glance at how a session is "feeling", in a status line and a live dashboard, without reading the transcript.

    For both, equally

    One shared picture and one shared configuration. The agent may tune its senses, but only inside bounds you set, and it can never switch one off.

    Design principles
    Every reading is 0..1 with a confidenceA guess never looks like a measurement. No data means low confidence, never an invented value.
    Metadata onlyTool name, success, exit code, token counts. Never prompts, code or tool output.
    Deterministic and localPure functions over events. No cloud, no database, no learning.
    Harness-agnostic coreOnly a thin adapter knows Claude Code. Codex is next.
    Architecture

    Hooks in, senses out.

    Claude Code hooks report what happens. An adapter turns that into a small, versioned event. Pure sensor functions read the events and your config, and the result reaches the agent over MCP and you in the dashboard and status line.

    Stack

    Deno + TypeScript. No runtime dependencies. No build step.

    Storage

    JSONL for events, readings and audit; JSON for config. All in .netsi-agent-senses/ in your project.

    Safety

    Dashboard on 127.0.0.1 only, behind a random token. Agent changes are bounded and audited.

    Get started

    Install in five minutes.

    You need Claude Code and Deno 2.x. Nothing to build.

    1. Clone the plugin

      shell
      $ git clone https://github.com/netsi1964/netsi-agent-senses.git ~/netsi-agent-senses

    2. Start Claude Code with it

      shell, in your project
      $ claude --plugin-dir ~/netsi-agent-senses

      Loads the hooks, the senses MCP server, /senses and the senses skill.

    3. Ignore the data folder

      shell
      $ echo ".netsi-agent-senses/" >> .gitignore

    4. Look at your senses

      Type /senses in Claude Code. Optional: add the status line (see the status line slide).

    who it is for

    • You work with Claude Code every day and want an early warning for failure spirals, a full context or a session running away with time.
    • You run agents for long stretches and want a shared, measurable picture of how they are doing.
    • You are curious whether the senses metaphor changes how an agent behaves.

    Check it works

    After a few tool calls, files appear in your project:

    .netsi-agent-senses/
    events.jsonl     # normalised events
readings.jsonl   # one snapshot per event
audit.jsonl      # who changed what
senses.json      # config (created on first use)
    Turn it down or off

    Disable a sense, pause it, or remove it all.

    Nothing is installed globally. The plugin lives in one folder, and its data lives in one folder per project, so every step below is easy to undo.

    Turn down or pause
    GoalHow
    Disable one senseUntick enabled in the dashboard, or set "enabled": false in senses.json. Only you can do this; the agent cannot.
    Pause the pluginStart Claude Code without --plugin-dir. No hooks, no MCP server, no data written.
    Stop the dashboardStop the server whose pid is in dashboard.json (below). It also stops when you restart your machine.
    .netsi-agent-senses/senses.json
    { "senses": { "time": { "enabled": false } } }
    stop the dashboard, in your project
    $ kill "$(sed -n 's/.*"pid": *\([0-9]*\).*/\1/p' .netsi-agent-senses/dashboard.json)"

    1. Remove the status line

      Delete the statusLine block you added to ~/.claude/settings.json.

    2. Delete the data in each project

      Events, readings, audit log and config. Export the audit log first if you want to keep it.

      shell, in your project
      $ rm -rf .netsi-agent-senses

    3. Delete the plugin

      shell
      $ rm -rf ~/netsi-agent-senses

      Optional: remove the .netsi-agent-senses/ line from your .gitignore.

    disabling instead of uninstalling

    A sense that fits your project badly, e.g. smell without linters, or time during an intended long autonomous run. Disabled senses are left out of the gut feeling.

    Sense 1 of 4 · bodily

    pain: it hurts when tool calls fail.

    The share of failed tool results in the last five minutes, weighted towards failures in a row. A failure spiral hurts more than scattered errors.

    How it is computed
    formula
    value = gain × (0.6 × failed/total
             + 0.4 × min(streak/3, 1))
confidence = min(results/5, 1)

    Failures come from Claude Code's PostToolUseFailure hook, with the exit code parsed from Exit code N. If you interrupt a tool yourself, that is not counted as pain.

    pain

    Always on. Most useful in debugging loops, where an agent tends to retry the same failing command with small variations. The skill tells it to stop, read the whole error, and change approach.

    Nine tool results in five minutes
    events.jsonl (simplified)

Bash  ok     exit 0
Bash  FAIL   exit 1
Bash  FAIL   exit 1
Bash  FAIL   exit 2
Bash  ok     exit 0
Bash  FAIL   exit 1
Bash  FAIL   exit 1
Bash  FAIL   exit 1   ← 3 in a row

    Sense 2 of 4 · bodily

    interoception: how full is my context?

    Context in use divided by the window size. The agent feels its context filling up before auto-compaction or degraded answers surprise it.

    Where the numbers come from
    SourceGivesConfidence
    Transcript, on every prompt and stoptokens in use (input + cache read + cache creation)0.5 when the limit is assumed (200k)
    Status line inputtokens in use and the exact window size, e.g. 1M1.0
    Earlier status line eventwindow size, carried forward0.9

    interoception

    Long sessions, big refactors and anything that reads many files. When it triggers, the skill tells the agent to finish the step, write a short state summary and suggest /compact.

    Sense 3 of 4 · temporal

    time: has this been going on too long?

    Session length, and how long the agent has worked alone since you last wrote. The default window of two hours counts as "long", and so do twenty minutes without hearing from you.

    How it is computed
    formula
    value = gain × max(age / window,
                   idle / (window / 6))
confidence = 1 with a prompt, 0.3 without

    time

    Autonomous runs and long tasks. When it triggers, the agent gives you a two-line status and asks whether to continue in the current direction, instead of drifting for an hour.

    A prompt, then ten minutes of work

    Sense 4 of 4 · classic

    smell: something in the code is off.

    When the agent runs a linter or type checker (deno lint, eslint, ruff, tsc, clippy and more), the adapter counts the problem lines in memory and stores only the count. Only the latest run per tool counts, so fixing the problems clears the smell.

    How it is computed
    formula
    value = gain × (1 − e^(−signals / 5))
confidence = min(measured results / 3, 1)

    No linter runs means no confidence. Smell never guesses.

    smell

    Projects with linters or type checkers. When it triggers, the agent fixes the reported problems before adding new code. No linters? Switch it off in the dashboard.

    The agent runs deno lint

    error[no-unused-vars]: `x` is never used

Found 2 problems
    what is stored
    { "kind": "tool_result", "tool": "Bash",
  "ok": true, "signals": 2 }
    senses_read → smell
    JSON
    {
  "id": "smell",
  "value": 0.753,
  "label": "7 lint/check signals in latest runs",

    Aggregator

    gut: one feeling from all senses.

    A weighted average of the enabled senses that have data. Its confidence is the weighted average of all senses' confidence, so when it is mostly guessing it says so.

    Default weights
    SenseWeight
    pain1.5
    interoception1
    smell1
    time0.5

    A value over threshold with confidence below 0.5 is flagged uncertain, and the label ends in "(low confidence)".

    gut

    Your quick glance. If it is high, the agent says which sense drives it. The individual senses are always shown next to it, so the aggregate never hides a single strong signal.

    senses_read → gut

  "confidence": 0.833,
  "triggered": true,
  "uncertain": false,

    The agent reads its own senses.

    senses_set · safety model

    The agent may tune. It may never go blind.

    Through MCP the agent can change only gain, threshold and window, only inside the bounds you set, and only with a reason. It can never change enabled, bounds or action, so it can never switch a sense off.

    Who may change what
    FieldAgentYou
    gain · threshold · windowwithin boundsyes
    boundsnoyes
    enablednoyes
    actionnoyes

    Shipped bounds are narrow on purpose. A fuzz test throws 5,000 random requests at the policy and checks no sense ends up blinded.

    senses_set

    When a sense is wrong for the task, e.g. pain firing on expected failures while writing tests first. Not to silence a sense that is telling the truth. The skill says exactly that.

    call
    senses_set {
  "sense": "pain", "threshold": 0.7,
  "reason": "Expected failures while writing tests first"
}
    result
    { "changed": [ { "field": "threshold", "from": 0.6, "to": 0.7 } ],
  "sense": "pain" }
    call
    senses_set { "sense": "pain", "threshold": 0.95, "reason": "too noisy" }
    result · isError
    Rejected: pain.threshold = 0.95 is outside the
human-set bounds [0.4, 0.85]
    call
    senses_set { "sense": "pain", "enabled": false, "reason": "quiet please" }
    result · isError
    Rejected: the agent may only change gain, threshold,
window; not allowed: enabled (only the human can
change these)

    /senses

    Whenever you wonder why the agent seems stuck, before deciding to /compact or start fresh, or at the end of a long session to see how it went.

    the status line

    Always, if you have room for it. It is the cheapest way to notice a sense going up while you are busy reading the agent's answer.

    Claude Code adapter

    Hooks record metadata, never content.

    Five Claude Code hooks feed the senses. They never block or slow the session down: any error is swallowed and the hook exits cleanly.

    What each hook records
    HookEvent
    UserPromptSubmitprompt + context usage from the transcript
    PreToolUsetool_call
    PostToolUsetool_result ok (+ lint count)
    PostToolUseFailuretool_result failed + exit code
    Stopturn_end + context usage
    A stored event, in full
    events.jsonl
    {"schemaVersion":1,"ts":1792446944603,
 "session":"a1b2c3","kind":"tool_result",
 "source":"claude-code","tool":"Bash",
 "ok":false,"exitCode":1}

    No prompt, no command, no output, no file path. A test replays recorded hook payloads full of secrets and checks that none of them reach the log.

    the hooks

    Automatically, as soon as the plugin is loaded. Deno runs with narrow permissions: it can write only the data folder and read only that folder and your transcripts.

    Skill

    A skill that says what to do with a feeling.

    A sense is only useful if it changes behaviour. The senses skill is plain markdown with rules per sense. Edit it to fit how you work.

    Sense over thresholdThe agent should
    painStop retrying. Read the last error in full, state its cause in one sentence, then change approach. Never run the same failing command a third time unchanged.
    interoceptionFinish the current step, write a short summary of state and next steps, and suggest /compact or a fresh session.
    timeGive you a two-line status and ask whether to continue in the current direction.
    smellFix the reported problems before adding new code.
    gutSay which sense drives it. If it is marked low confidence, check the senses first.
    skills/senses/SKILL.md (excerpt)
    ## Tuning your own senses
- Tune a sense when it is wrong, not when it
  is inconvenient.
- Never tune a sense to silence a true signal.
- Prefer small steps, and say what you changed
  and why.

    the skill

    Loaded automatically with the plugin. Claude picks it up when a sense triggers, when tool calls keep failing, or before it calls senses_set.

    senses.json

    One small file you can partially override.

    Write only what you want to change: everything else comes from the defaults. Edits apply without a restart. An invalid file is ignored, the last valid config stays in use, and the dashboard shows why.

    .netsi-agent-senses/senses.json
    {
  "senses": {
    "pain": {
      "threshold": 0.5,
      "bounds": { "threshold": [0.3, 0.9] }
    }
  }
}

    Triggers earlier, and gives the agent more room to tune.

    .netsi-agent-senses/senses.json
    {
  "senses": { "smell": { "enabled": false } },
  "gut": { "weights": { "interoception": 2 } }
}

    Smell off, and context weighs double in the gut feeling.

    Fields per sense
    enabledOff: no reading, no part in gut
    gainMultiplies the raw value
    thresholdValue at which it triggers
    windowSliding window in seconds
    boundsThe agent's room for the three above
    actioninform, warn, block or influence
    Accountability

    Every change has a who, a when and a why.

    Each config change, by you in the dashboard or by the agent over MCP, is written to an append-only audit log with the actor, the old and new value, and the reason. Logs rotate at 5 MB.

    An agent change
    audit.jsonl
    {
  "ts": 1792450100000,
  "actor": "agent",
  "type": "config_change",
  "sense": "pain",
  "from": { "threshold": 0.6 },
  "to": { "threshold": 0.7 },
  "reason": "Expected failures while writing tests first"
}
    Export

    Click Export audit log in the dashboard to download the full log as JSONL, or read the file directly. The dashboard also shows the 50 latest changes in a table, with agent rows marked in text.

    the audit log

    When you want to know why a sense stopped triggering, review what the agent changed overnight, or explain a session afterwards.

    Open source

    Build your own senses. Bring your own harness.

    A sense is a pure function from events to a reading. An adapter is the only code that knows a harness. Both are documented and tested against recorded sessions.

    A new sense in ~20 lines
    src/core/sensors/my-sense.ts
    export const mySense: Sensor = {
  id: "my-sense", human: "balance", category: "bodily",
  compute({ events, config, now }) {
    const recent = inWindow(events, config, now);
    if (!recent.length)
      return { value: 0, label: "no data", confidence: 0 };
    // … your rule
    return { value: raw * config.gain, label, confidence };
  },
};
